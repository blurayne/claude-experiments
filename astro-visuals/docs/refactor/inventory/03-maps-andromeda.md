## Randomness consumed at module-evaluation time (parity-critical)

1. **Line 2365, `setGalaxy(1)`** — the whole boot-time scene build. At eval time both `galaxyMap` and `m31Map` are `null`, so the key is `'pq1'` and the branch taken is `genGalaxy(1)` (1698) followed by `genAndromeda(1)` (2162). Together those draw on the order of 10⁶ `Math.random()` values, in a fixed sequence: galaxy stars → galaxy nebulae → galaxy dust → M31 bulge → M31 inner disk → M31 arms. **Nothing else in this slice consumes randomness at eval time.** Everything before it in the slice (lines 1889–2364) is pure declarations plus GL program creation.
2. **Line 2362–2364** consumes no randomness but must run before 2365 only for GL-state reasons; reordering 26 and 27 relative to each other does not change the random stream, but reordering 27 relative to *any other* slice's eval-time random consumer does.
3. Indirect, post-eval but still order-sensitive: `loadGalaxyMap()` and `loadM31Map()` are invoked at **3051/3052** (outside this slice). Each resolution calls `flushGxyCache(); setGalaxy(curD)` (1929–1930 and 2356–2357), i.e. a *second and third* full regeneration whose ordering depends on network/decode timing. The number and order of `Math.random()` calls after boot is therefore already race-dependent in the current file. A screenshot-parity harness must either block until both maps resolve or block both fetches; it cannot be left to chance, and this is not something the refactor introduces — record it so nobody blames the refactor for it.
4. `mapPick` (1934), `mapXZ` (1940), `mapXZ31` (2153) are the per-sample random consumers. `mapXZ`/`mapXZ31` draw **two uniform and two gaussian** values per call and `gauss()` (1649) itself loops on `Math.random()` until non-zero — so the number of draws per sample is not fixed. Any change to the call order inside `genGalaxyMap`/`genAndromedaMap` (including hoisting a `mapPick` out of a loop) shifts the entire downstream stream.

## Boot-order hazards

1. **`setGalaxy(1)` at 2365 reaches forward to `loadGaiaDeep` (3043) — and is only safe because D is 1.** `setGalaxy` ends with `if(D >= 5) loadGaiaDeep();` (2066). `loadGaiaDeep` is a hoisted function declaration, so the call itself would resolve, but its first statement reads `deepAsked`, a `let` declared at **3042** — 677 lines later. At eval time that is a TDZ throw. The file documents this at 6156–6161 ("load-order trap"). Any refactor that changes the boot density, or that lets a persisted setting reach line 2365, kills the page. Keep the literal `1`.
2. **`genAndromedaMap` (2195–2285) reads `M31_ARM_K`, declared at 2292 — after it.** Safe today only because `genAndromedaMap` is never called before `m31Map` exists, which is after the whole script has evaluated. If a bundler hoists `setGalaxy(1)` past the M31 loader, or if anything ever calls `genAndromedaMap` synchronously during evaluation, this is a TDZ throw on a `const`.
3. **`setGalaxy` (2040) is defined 122 lines before `genAndromedaMap` (2195) and `genAndromeda` (2162) and calls both.** Function declarations hoist, so this works in one script; across ES modules it becomes an import cycle (`scene/cache` ↔ `scene/andromeda`). Same for `loadGalaxyMap` (1891) calling `setGalaxy` (2040), and `loadM31Map` (2293) calling `flushGxyCache` (1858, previous slice).
4. **The comment at 2139–2140 is a load-order contract, not a note:** "setGalaxy(1) is called after the Andromeda section below: its constants (R_A, the satellite offsets) are const bindings the generator needs live." `genAndromeda` reads `R_A` (2151) and `genAndromedaMap` reads `M32_C`/`M110_C`/`GSS_DIR` (2159–2161). Because these are `const`, moving the initial build above line 2161 is a TDZ death, silently invisible to a parse check.
5. **`M31_MAP_SCALE` (2152) is computed from `R_A` (2151) at evaluation time.** If `R_A` moves to `astro/constants` and `M31_MAP_SCALE` to `scene/galaxymap`, the import must be a value import evaluated before the module body — trivially true for ESM, but not if either becomes a lazily-assigned `let`.
6. **`MERGE_T0`/`MERGE_T1` (2435) are computed at evaluation time from `AGE0` (1541) and `YR_PER_SIM` (1540)**, which are in an earlier slice. `astro/merger` must therefore be evaluated after `astro/constants`; a circular import between them would leave both as `undefined` and produce `NaN` spin with no error at all — the worst failure shape for a screenshot gate.
7. **`mergeAt` (2428) is a `const` arrow, not a function declaration**, so it does not hoist. It is called from 2450 (in-slice), 2982 and 6140. All current call sites are inside functions invoked post-evaluation, but the asymmetry with the surrounding `function` declarations is exactly the trap that has already killed this page: converting any nearby function declaration to an arrow, or vice versa, changes hoisting behaviour.
8. **`updateAnd` (2442) calls `ageGyr` (2942), which reads `simT` (`let`, 5029).** Three slices deep, and all of it lazy. `astro/merger` is supposed to be pure; as written it reaches into render state. Extract it by passing the age in, or the module graph gains an `astro → render` edge that must not be a cycle.
9. **The `for…of` at 2362 leaves `pDust` as the currently bound GL program** and leaves `uGRot` set on all three programs. The draw passes at 5434+ and 5484+ re-bind explicitly, so nothing depends on the residue today — but the loop is a bare eval-time statement whose ordering relative to `setGalaxy(1)` is load-bearing for nothing, and relative to program creation (2081, 2116) is load-bearing for everything. It belongs in `main.ts`, not in a module body.
10. **`loadGalaxyMap` and `loadM31Map` race each other into `flushGxyCache`** (documented at 1855–1857). Whichever resolves second flushes VAOs the first has just published. This works only because `flushGxyCache` is total and `setGalaxy` immediately re-publishes. Splitting the two loaders into different modules must not introduce any await/microtask between the flush and the rebuild.
11. No element ids are read anywhere in this slice — the id-drift failure mode does not apply here. The only DOM touch is `document.createElement('canvas')` at 1895 and 2297, which is id-free and safe.
